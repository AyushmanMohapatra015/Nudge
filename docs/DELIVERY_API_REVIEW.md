# B4: delivery-plan API implementation and verification

October15,2026. app/api/delivery-plan/route.ts and lib/delivery-plan-actions.ts implement the local schedule API. Bryntum Gantt is still not installed or rendered. No actual workspace, provider, account, licence, external message or credit was used by this verification.

## Implemented behavior

- GET /api/delivery-plan reads existing local records only, without seeding a workspace or reconciling PayPal. Returns404 if absent; owner authentication is required in sandbox. Simulation follows the existing unauthenticated demo model and cannot select sandbox records through a browser query/body. Render preparation requires sandbox mode for hosted owner access.
- Responses are no-store and contain workspace version, local snapshot time, stateSource=local-records, remoteCheckedAt=null, validated plan/read status, stale-preview flag and minimal extra/invoice context. Invoice identities, pay URLs, client email/tokens, full agreements/analysis, private audit and owner credentials are excluded. Multiple invoices remain separate rows, with exact stored cents and pending-outcome flags. Snapshot time is not a live PayPal check.
- POST checks same-origin, owner session, shared process-local action quota and a32KiB bounded UTF-8 body; rechecks session after reading. Strict schemas reject unknown fields, financial commands, missing confirmation and browser-supplied saved plans/diffs.
- Stage requires expectedWorkspaceVersion, expectedPlanRevision and expectedPreviewId (null if absent), plus calendar/candidate. Tasks use key=new:local-key or a server task UUID already in current/expected preview; dependencies use predecessorKey/successorKey. The server generates new canonical UUIDs and computes the review diff. New UUIDs invented by a browser are rejected. Task kind/scope/proposal identity cannot be rewritten under an existing key.
- Apply/discard require expectedWorkspaceVersion, previewId and confirmed=true. Apply uses the stored candidate, checks its exact staging version and current acceptance/schedule rules, preserves original, advances current revision and consumes preview. Discard consumes only that preview; revision0 returns to unconfigured, later current/original remain intact. A stale preview can be discarded after refresh, but cannot be applied without restaging.
- Each command runs synchronously in BEGIN IMMEDIATE with an existing-row read, idle/version checks, one version increment and one bounded audit entry. Response projection is validated before COMMIT, so a malformed projection rolls back state/audit/version too. Missing workspaces are never auto-seeded. Duplicate or competing commands reject409; no automatic write retry.
- Malformed stored schedules yield review-needed on GET and block mutations409 without deleting the record. Other database/projection failures produce generic503 without raw details. Invalid command/body returns400, oversized413, request-body timeout408, unauthorized401, cross-site403, quota429 with Retry-After. Process-local limiting is not a shared/distributed hosting defence.

Existing client approval/financial routes and webhook logic are unchanged. Scheduling never changes invoices, proposals, policies, client commitments, payment promises or remote-operation/event tables. A payment or client-decision mutation makes the old preview stale through the shared workspace version; accepted prices alone do not approve a schedule automatically.
