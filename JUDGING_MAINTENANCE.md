## Bounded routine on an approved deployment

1. Confirm you are examining the intended service and fictional judging workspace. If no deployment was approved, record not applicable; do not create one to complete this checklist.
2. Check the configured health endpoint and inspect generic status only. Nudge's /api/health performs a local database query and may initialise an empty schema on first use. A200 does not prove the right mounted disk, retained records, provider access, working chart licence or successful payments.
3. Check a permitted native reading path without starting model calls, invoices or reminders. Analytics reads stored records. Respect authentication and private bearer links; use the approved private access channel. Do not publish reusable owner credentials, client tokens or a database download link.
4. Review actual accrued hosting usage, projected remaining coverage and sponsor expiry/usage displays. Unchanged visible credits are not proof of no accrued charges. If there is uncertainty, pause new optional work and review account terms with the owner; do not upgrade, add a card or purchase capacity automatically.
5. Review only sanitised operational signals. Do not paste raw logs, request headers, environment values, licence strings, client URLs or screenshots containing account details into public issues or the repository. Report verified functionality separately from degraded/held providers.
6. An attended provider/end-to-end test requires the appropriate allowance, permission and explicit bounded test approval. No daily model warm-up, repeated sandbox checkout or automatic financial write is authorised by this document. Preserve the selected payment fixture and webhook evidence.

This is a single-owner/shared-workspace prototype, not isolated judge accounts. Arrange the approved review method and explain shared state. Do not reset records while someone is reviewing or while remote outcomes are uncertain. Client links expire/rotate; verify their actual approved validity before judging, not by removing expiry safeguards.

## Owner-approved shutdown sequence — preparation only

1. Confirm judging/organiser obligations, approved evaluation periods and whether continued access is needed. Ask for any extension before relying on it. Record an explicit owner decision; do not shut down an active judge demo automatically at a guessed deadline.
2. Stop new user mutations/provider work and resolve or record uncertain remote operations. Take and verify an appropriate private snapshot if retention is authorised; record the retention/deletion decision without publishing data.
3. Disable live AI entry points and review approved webhook/integration handling before removing access. Revoke or rotate relevant service credentials only as an explicitly approved account action; never publish values or treat deleting an env file as revocation.
4. For any actual hosted resources, inspect compute, disks, storage, build/workflow and other active items in the correct workspace. Verify the account-specific consequences and residual billing before stopping/removing anything. A stopped web endpoint is not proof that all costs have ended. Resource deletion/data destruction requires a separate concrete approval.
5. Verify intended public endpoints/access are closed or remain available as explicitly approved; inspect billing/resource status and retain a non-sensitive completion record. Do not claim a subscription cancelled or a balance settled without account evidence.
6. Keep the original application source under its licence, with commercial dependencies clearly separate. Never upload vendor distributions, generated bundles, credentials or private sponsor correspondence as a shutdown archive. After the approved Bryntum period, discontinue that evaluation use unless a separate licence/extension is agreed.
